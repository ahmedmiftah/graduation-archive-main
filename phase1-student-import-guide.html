01

نظرة عامة

الفجوة الجوهرية المكتشفة أثناء الفحص: النظام كان يحتوي 3 أدوار فقط، ولا يوجد أي مفهوم "حساب طالب يسجّل دخول" — الطلاب كانوا بيانات وصفية فقط داخل جدول project_students الأرشيفي.

هذا يعني أن Phase 1 لم يكن "بناء ميزة استيراد" فحسب — كان توسيعًا فعليًا لنموذج الهوية بأكمله في النظام: دور Spatie جديد (student)، جدول مستقل بالكامل، وآلية دخول لم تكن موجودة إطلاقًا من قبل (تسجيل دخول برقم قيد بدل بريد إلكتروني).

02

جدولان منفصلان تمامًا — لا دمج

قرار معماري محسوم مبكرًا: عدم لمس project_students إطلاقًا.

project_students (موجود من قبل)
بيانات أرشيفية وصفية فقط — أسماء طلاب ضمن مشروع منجز، بلا أي حساب دخول، ولم تُعدَّل بنيته إطلاقًا.
students (جديد بالكامل)
سجل هوية حي: full_name, national_id, registration_number, department_id, specialization_id, semester, academic_year, date_of_birth, user_id (nullable FK).
⚠️ الخلط بين الجدولين كان سيعني إما كسر بيانات الأرشيف القديمة، أو إجبار كل سجل أرشيفي قديم على امتلاك حساب دخول وهمي — كلاهما مرفوض. الفصل التام هو الحل الوحيد المتّسق مع قاعدة "لا كسر لما هو موجود".
03

آلية إنشاء الحساب

حقلان موجودان أصلًا في بيانات الطالب أصبحا اسم الدخول وكلمة المرور المؤقتة — بلا أي حقل جديد إضافي للمصادقة.

اسم الدخول
registration_number

رقم القيد كما هو، بلا أي تحويل ظاهر للطالب.

كلمة المرور المؤقتة
date_of_birth → DDMMYYYY

مثال: مولود 2003-05-14 ← 14052003

عند نجاح الاستيراد، يُنشأ سجل Student ثم — إن مرّ التحقق — حساب User مرتبط عبر user_id، مع force_password_change = true فورًا، وإشعار StudentAccountCreated يُرسَل للحساب الجديد.

04

تحويل رقم القيد إلى بريد داخلي — لماذا احتجنا لمس كود مشترك

Laravel's Auth::attempt() يتوقّع بريدًا إلكترونيًا كحقل تعريف فريد — الطالب يكتب رقم قيد. الحل: توليد بريد تركيبي غير حقيقي.

أي مدخل بلا @ يُعامَل كرقم قيد ويُحوَّل للبريد التركيبي المرتبط، قبل استدعاء Auth::attempt()
// LoginRequest::resolveLoginEmail() — أصغر تعديل ممكن على كود حسّاس مشترك if (!str_contains($input, '@')) { $student = Student::where('registration_number', $input)->first(); $input = $student?->user?->email ?? $input; // بريد حقيقي يمرّ دون أي تغيير }

لا مفر تقنيًا من لمس هذا الملف — الطالب يكتب رقم القيد لا البريد التركيبي، ولا سبيل لتعليم Auth::attempt() التعرّف على رقم القيد مباشرة دون طبقة تحويل قبله. اختير هذا كأضيق تعديل ممكن، واختُبر صراحة بـ8 اختبارات (StudentLoginTest.php) لضمان عدم كسر دخول الموظف بالبريد الحقيقي.

05

معالج الاستيراد — نمط Preview ثم Confirm

لا صف يُكتب في قاعدة البيانات أثناء المعاينة — القسم يرى النتيجة الكاملة قبل أي التزام.

الخطوةماذا يحدثكتابة فعلية؟
1. تنزيل القالبملف Excel بالأعمدة المطلوبةلا
2. رفع للمعاينةكل صف يُفحَص، النتيجة (صالح/غير صالح + السبب) تُعرَض كاملةلا — dry run كامل
3. تأكيد الاستيرادالصفوف الصالحة فقط تُكتب: Student + User + إشعارنعم

كل عملية استيراد تُسجَّل في imported_student_batches (الدفعة) وimported_student_rows (سجل تدقيق صفًا بصف — أي صف فشل ولماذا) — تتبّع كامل قابل للمراجعة لاحقًا، لا مجرد رسالة نجاح/فشل عابرة.

06

طبقات التحقق

أربع طبقات مستقلة، كل صف يمر بها جميعًا قبل أن يُعتبَر صالحًا.

  • يتحقق طول رقم القيد يطابق system_settings.registration_number_length — إعداد نظام قابل للتعديل، لا رقم ثابت في الكود
  • يتحقق الرقم الوطني 12 رقمًا بالضبط
  • يرفض تكرار رقم وطني أو رقم قيد داخل نفس الملف — يفشل الصف الثاني فقط، الأول يمر
  • يكتشف طالبًا موجودًا مسبقًا في النظام (بلا تكرار سجل) بدل رفض الصف كخطأ
07

قرار أمان صريح ومقصود

كلمة المرور المؤقتة مبنية على بيانات شبه-عامة — قرار مستخدم واعٍ رغم التحذير.

⚠️
الرقم الوطني وتاريخ الميلاد بيانات شبه-عامة نسبيًا (قد تكون معروفة لأطراف أخرى). استخدام تاريخ الميلاد ككلمة مرور مؤقتة اختيار المستخدم صراحة رغم توضيح هذا التحذير أثناء التخطيط. الحد الأدنى التعويضي: force_password_change = true يمنع أي تصفّح فعلي للنظام قبل تغييرها إجباريًا عند أول دخول.
