02

إنشاء الحساب

لا يوجد تسجيل ذاتي للطالب — الحساب يُنشأ تلقائيًا فقط عبر استيراد القسم.

اسم الدخول
registration_number

رقم القيد كما هو، بلا أي تحويل.

كلمة المرور المؤقتة
date_of_birth → DDMMYYYY

مثال: مولود 2003-05-14 ← 14052003

البريد المخزَّن داخليًا
{registration_number}@students.local

معرّف تقني فقط — الطالب لا يراه ولا يستخدمه.

عند أول دخول
إجبار تغيير كلمة المرور

force_password_change = true

03

آلية تسجيل الدخول

نفس صفحة الدخول الموحّدة لكل الأدوار — الفرق فقط في ما يُكتب بخانة "البريد".

حقل الدخول يقبل نصًا عامًا. إن احتوى المدخل على @ يُعامَل كبريد حقيقي (الموظفون/المشرفون) دون أي تغيير. إن لم يحتوِ عليه، يبحث النظام عن Student برقم القيد المطابق، ويستخدم بريد حسابه الداخلي للمصادقة الفعلية — منطق Auth::attempt نفسه لم يتغيّر.

بعد نجاح الدخول، ميدل وير EnsurePasswordIsChanged يفحص force_password_change على كل طلب. إن كان مفعّلًا، يُحوَّل الطالب إلى صفحة تغيير كلمة المرور مهما كانت الصفحة المطلوبة — باستثناء صفحة التغيير نفسها وتسجيل الخروج.

06

المقترح وربط الفريق

آلية الربط التلقائي هي جوهر بوابة الطالب — لا يوجد أي إجراء يدوي لربط طالب بمقترحه.

عند إنشاء المقترح، يُدرَج الطالب المسجّل دخوله تلقائيًا كعضو في الفريق حتى لو لم يذكر نفسه — هذا يحدث داخل EnsuresStudentTeamMembership قبل التحقق من صحة الطلب مباشرة، لا داخل الكونترولر لاحقًا.

لكل زميل آخر يُذكَر بالاسم ورقم القيد، يبحث ProjectProposalRepository عن سجل Student مطابق لرقم القيد ويربطه تلقائيًا عبر student_id. النتيجة: كل عضو فريق مرتبط بحساب حقيقي يرى نفس المقترح بالضبط — رؤية جماعية، لا حصرية على من ضغط "حفظ".

لا جدول تتبّع منفصل يحتاج مزامنة — كل مرحلة تُحسب حيًّا من حالة المقترح والمشروع الفعلية عبر LifecycleTimelineService.

  1. ✓
    اختيار المشرف
    مكتملة — supervisor_id غير فارغ
  2. ✓
    تقديم المقترح
    مكتملة دائمًا بمجرد وجود سجل المقترح
  3. ●
    مراجعة المشرف / مراجعة القسم
    الحالية — الحالة ما زالت pending
  4. اعتماد المقترح
    قادمة — تنتظر status = approved

08

الصلاحيات وقواعد العمل

كلها في ProjectProposalPolicy — الطالب لا يملك أي مسار يتجاوزها.

  • يسمح رؤية وتعديل مقترح فريقه فقط، عبر تطابق student_id
  • يسمح تعديل المقترح أثناء pending أو needs_revision فقط
  • يمنع إنشاء مقترح ثانٍ أثناء وجود مقترح نشط
  • يمنع رؤية أي مقترح لفريق آخر
  • يمنع تغيير حالة المقترح (اعتماد/رفض) — يبقى حصرًا لـdept_manager
  • يمنع الحذف نهائيًا
  • تنبيه الملفات تُستبدَل عند كل رفع جديد — لا تاريخ إصدارات (قرار مقصود)
