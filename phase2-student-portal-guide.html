02

إعادة استخدام Browse.vue بدل تكرارها

صفحة /student العامة تعرض نفس محتوى "تصفّح المشاريع" — لكن بدون نسخ الكود.

PublicController::browse() أُعيد بناؤه حول دالة خاصة مشتركة renderBrowse(). الإجراء الجديد studentPortal() يستدعي نفس الدالة بقيم مختلفة فقط لـrouteName وloginLabel — يُصيَّر نفس مكوّن Public/Browse.vue بالضبط، بخصائص اختيارية جديدة (قيمها الافتراضية تحافظ على سلوك /browse الأصلي حرفيًا دون أي تغيير).

صفحة /browse الأصلية لم تُمسّ إطلاقًا — لا اختبار واحد من اختباراتها القديمة احتاج تعديلًا.

03

حساب دورة حياة 17 مرحلة — بلا جدول تتبّع

القرار الأهم في هذه المرحلة: لا lifecycle_progress منفصل يحتاج مزامنة يدوية عند كل تغيير حالة.

  1. ✓
    اختيار المشرف
    مكتملة — supervisor_id غير فارغ
  2. ✓
    تقديم المقترح
    مكتملة بمجرد وجود سجل المقترح
  3. ●
    مراجعة المشرف / القسم
    الحالية — الحالة ما زالت pending
  4. اعتماد المقترح
    قادمة — تنتظر status = approved
  5. بدء المشروع ← إنجازه
    تتبع وجود Project ثم current_status_id

LifecycleTimelineService::build($proposal) يعيد مصفوفة من 17 عنصرًا، كل واحد بحالة done/current/upcoming — كلها مشتقة من نفس عمودين موجودين أصلًا: ProjectProposal.status (5 حالات نصية) وProject.current_status_id + ProjectStatus.sort_order. بعض المراحل (رفع التوثيق، موافقة المشرف، التدريب الميداني، إخلاء الطرف) تبقى "قادمة" للأبد حاليًا — لا نظام مقابل مبني بعد، وهذا مقصود ومُفصَح عنه، لا خطأ.

04

لماذا Trait لا منطق داخل الـController

عطل اكتُشف أثناء البناء: قاعدة "على الأقل طالب واحد بالفريق" كانت تفشل قبل أن يصل الطلب للـController أصلًا.

// المشكلة: FormRequest يُتحقَّق منه قبل تنفيذ الـController // students: required|min:1 ← يفشل فورًا إن أرسل الطالب مصفوفة فارغة // الحل: EnsuresStudentTeamMembership trait protected function prepareForValidation(): void { // يُدرِج الطالب نفسه في students[] هنا — قبل التحقق، لا بعده }

Laravel يُنفِّذ تحقّق FormRequest قبل استدعاء أي كود داخل الـController — أي منطق لإدراج الطالب نفسه في فريقه داخل store() كان سيصل متأخرًا جدًا. النقل لـprepareForValidation() ضمن Trait مشترك حلّ المشكلة جذريًا، وأزال الحاجة لمنطق مكرَّر داخل Student\ProposalController.

05

ربط الفريق التلقائي عبر رقم القيد

لا إجراء ربط يدوي — أي زميل يُذكَر برقم قيد مطابق يُصبح عضوًا فعليًا برؤية مشتركة.

ProjectProposalRepository::withResolvedStudentId() يبحث عن سجل Student مطابق لرقم القيد المذكور في كل صف فريق، ويربطه عبر student_id على ProjectProposalStudent. النتيجة: كل عضو فريق له حساب حقيقي يرى نفس المقترح بالضبط من حسابه الخاص — لا حصرية على من ضغط "حفظ" فقط.

06

قواعد العمل

كلها في ProjectProposalPolicy — فرع student مخصَّص.

  • يسمح رؤية وتعديل مقترح فريقه فقط، عبر تطابق student_id
  • يسمح التعديل أثناء pending أو needs_revision فقط
  • يمنع مقترحًا ثانيًا أثناء وجود مقترح نشط (hasActiveProposal())
  • يمنع رؤية أي مقترح لفريق آخر
  • يمنع تغيير حالة المقترح — يبقى حصرًا لـdept_manager
07

قرار مسجَّل صراحة — لا Versioning للملفات بعد

مخالفة واعية للطلب الأصلي، بموافقة المستخدم صراحة.

الملف القديم لا يزال يُستبدَل عند كل رفع جديد (لا نظام إصدارات v1 → v2 → v3 فعلي للملفات نفسها). كذلك تقييد /projects و/search عن دور student بقي مؤجَّلًا من Phase 1 — لم يُعالَج في هذه المرحلة أيضًا، بقرار مستخدم صريح.
