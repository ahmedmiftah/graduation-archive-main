01

نظرة عامة

الطالب يرسل رسالة طلب انضمام لفكرة معيّنة → المشرف صاحب الفكرة يقبل أو يرفض من صفحة مراجعة مخصَّصة لكل فكرة.

02

نمط Policy لنموذج فرعي مرتبط بنموذج أب

تحدٍّ تقني حقيقي: كيف تُخوِّل "إنشاء طلب" حين الـability تخص نموذجًا (Request) لكنها تعتمد على نموذج آخر (Idea) له Policy منفصلة أصلًا؟

// الاستدعاء الخاطئ البديهي — يُحلّ عبر ProjectIdeaPolicy وليس المطلوبة! // $this->authorize('create', $idea); ← يستخدم سياسة Idea، لا Request // الحل: نمط Laravel القياسي لمورد فرعي مرتبط بأب $this->authorize('create', [ProjectIdeaRequest::class, $idea]); // العنصر الأول في المصفوفة يحدِّد الـPolicy فقط (لا يُمرَّر كوسيط) // الباقي يُمرَّر للدالة: create(User $user, ProjectIdea $idea)

هذا النمط موثَّق رسميًا في Laravel لسيناريو "إنشاء تعليق مرتبط بمقال" — نفس المبدأ هنا: ProjectIdeaRequestPolicy::create() تستقبل ProjectIdea كوسيط ثانٍ رغم أن الـPolicy المُستهدَفة هي ProjectIdeaRequest.

03

منع التكرار وقاعدة الالتزام الواحد

ثلاثة شروط مستقلة يجب أن تمر جميعًا قبل قبول طلب جديد.

  • يمنع إن كانت الفكرة ليست available
  • يمنع إن كان لدى الطالب مشروع نشط بالفعل (hasActiveProposal() الموجودة من Phase 2)
  • يمنع إن كان لدى الطالب طلب معلَّق أو مقبول لنفس الفكرة تحديدًا (لا يمنع طلبات لأفكار أخرى مختلفة)
04

تحوّل حالة الفكرة تلقائيًا عند القبول

القبول له أثران فوريان: على الطلب، وعلى الفكرة نفسها.

دائمًا
الطلب → accepted
←
إن لم يكتمل العدد
الفكرة → reserved
←
إن اكتمل العدد
الفكرة → closed

الشرط الفاصل: عدد الطلبات المقبولة مقارنة بـrequired_students_count. إن كان العدد المطلوب 1 (الحالة الافتراضية)، القبول الأول يُغلق الفكرة مباشرة.

06

حد الصلاحية المحسوم مع Phase 7

القرار الأهم في هذه المرحلة: ماذا "لا" تفعل، لا فقط ماذا تفعل.

  • قرار القبول لا ينشئ ProjectProposal أو Project فعليًا — يقتصر على تحديث حالة الطلب والفكرة فقط
  • سبب نص الخطة الأصلية ينص أن جدول proposal_reservations (Phase 7) هو من "يربط الطالب بالفكرة تحديدًا" رسميًا — تنفيذ ذلك هنا كان سيكرِّر منطقًا سيُعاد بناؤه بشكل مختلف لاحقًا
